# AutoDub MVP Architecture

## Purpose and status

This file is authoritative for technical boundaries and data flow. It describes the agreed local MVP design; implementation exists only when `TASKS.md` records verified completion.

## Components

| Component | Owns | Must not own |
| --- | --- | --- |
| React + TypeScript + Vite | Upload UI, project list, job state, translation editing, artifact preview/download | Secrets, direct access to application tables, or direct Whisper/FFmpeg execution |
| FastAPI | HTTP validation, SQLAlchemy persistence calls, job creation, status/result endpoints | Full media processing inside a web request |
| Supabase-hosted PostgreSQL | Metadata for `Project`, `Job`, `Segment`, translation revision, `Artifact`, and persisted state/errors | Large video/audio/output file contents |
| Python worker | Sequential job claiming; Whisper, Gemini, Edge-TTS, FFmpeg; persisted stage/result updates | Dependence on an open browser tab |
| Local storage | Source, intermediate, and result files isolated by server-generated project/job IDs | Arbitrary client-selected filesystem paths |

Frontend calls FastAPI only. FastAPI and the worker access Supabase-hosted PostgreSQL through SQLAlchemy with a PostgreSQL driver, using `DATABASE_URL` from uncommitted environment configuration. A separate worker process on the same Windows machine claims one job at a time and writes state/results back to PostgreSQL and local storage.

## Pipeline A — Transcribe and translate

1. FastAPI streams an uploaded source into UUID-controlled local storage, enforcing the configured byte limit, then uses `ffprobe` to validate an actual MP4 video and its configured duration limit before persisting the Project. The canonical limits are in `docs/PRD.md` and backend configuration.
2. The worker resolves only the Project's UUID-derived source path under managed storage and runs faster-whisper model `small`.
3. It validates and transactionally persists ordered Segments with stable IDs, timestamps, and source text. Re-transcription replaces only unedited Segments for the same Project revision; translated, revision-changed, or warning-bearing Segments are preserved and cause a safe failure.
4. Before Whisper starts on a combined translation Job, the worker lists the configured model catalog and checks that `GEMINI_MODEL` is listed with `generateContent`; this catches an invalid/unsupported identifier but does not prove the Google project has inference entitlement, billing eligibility, or permission. Google documents that `models.list` does not check those gates. The developer can run `python scripts/gemini_diagnostics.py list` from `backend` to discover IDs; a one-request model probe requires explicit `--confirm-live`. The client explicitly uses the Gemini Developer API (`v1beta`) and disables SDK automatic function calling for requests that declare no tools. For a non-empty transcript, the worker builds an ordered immutable translation snapshot containing stable Segment UUIDs, source text, positions, exact persisted start/end timestamps, and source durations. It first attempts one full-transcript Gemini request when configurable Segment/source-character ceilings and conservative local input/output budgets fit. Otherwise it sends deterministic ordered batches with up to two adjacent context-only Segments on each side; only target batch IDs may appear in the structured response. The current defaults are 500 Segments / 120,000 source characters for bulk eligibility, 262,144 estimated input tokens, 16,384 output tokens, 40 target Segments per fallback request (maximum 100), and 24,000 source characters per fallback request including context. Token estimates use UTF-8 byte counts locally and do not call provider token-counting endpoints. Each request applies the configured output-token cap and a 120-second SDK timeout. SDK automatic retries are disabled so TRANS-02 controls the only allowed retry. App budgets must remain within the selected model's published limits. The complete ID-to-translation mapping is validated before transactionally updating only `translated_text`; no-speech input skips Gemini.
5. After all translations persist, the combined Job finishes successfully. A no-speech transcript finishes with the truthful `no_speech` stage.

Gemini requests fail immediately on quota/rate-limit and permanent configuration/client errors. Transient network or provider 5xx failures retry the same request at most once after a 0.5-second bounded delay; malformed or incomplete structured output is also retried once, then rejected. Persisted Job errors report sanitized model/status/reason guidance and retryability, never raw provider payloads or credentials. `POST /projects/{project_id}/translation-retry-jobs` can queue translation over an existing current transcript only when all ordered Segments are valid and untranslated; the separate worker skips Whisper and reuses the same atomic translation service. Edited/saved translations are rejected, and IDs, source text, timestamps, and artifacts are not modified. No quota retry, model switch, fallback text, or partial persistence is allowed. Translation logs include only safe counts, estimated request sizes, classified retry categories, elapsed time, and model/job IDs; source transcript content and credentials are never logged. These are request-shaping guarantees, not a claim of translation-quality improvement; real-output quality comparison belongs to TRANS-04.

## Pre-TTS validation (EDIT-03)

`GET /projects/{project_id}/tts-readiness` reads the current Project, Jobs, and ordered persisted Segments without writing data or changing Job state. Readiness requires at least one Segment, no queued/running Job, and a latest Job that succeeded with `translation_ready` for the current Project revision. Historical terminal Jobs do not count as active. Segment checks require valid unique UUIDs, non-empty source text, current revision, timestamps convertible to non-negative integer milliseconds with end after start, and a non-empty Vietnamese translation no longer than the shared 10,000-character EDIT-02 limit. The database stores source timestamps in seconds as `Numeric(12,3)`; validation interprets that millisecond precision without modifying it.

Blocking validation issues make `ready` false. Timing concerns are warnings only: speaking windows shorter than 250 ms, translation density above 8 whitespace-delimited Vietnamese tokens per source second, and overlaps with earlier source timestamp windows. WPS is a pre-TTS heuristic, not measured speech duration; long translations are not rejected solely for their original window. The viewer separates errors from warnings, allows navigation to affected Segments, and clears previous results after a successful translation edit so the user must validate again.

EDIT-03 preserves the original Whisper timeline and creates no output timeline. It does not synthesize audio, measure TTS duration, adapt speaking rate, stretch video, shift timestamps, or create artifacts. Future TTS/Render work must measure generated audio and calculate any output timing separately.

The worker loads and reuses one Whisper model instance per process. It attempts CUDA `float16` inference, logs the reason if CUDA initialization/inference fails, and falls back to CPU `int8`. CPU inference is verified; GPU inference is not claimed unless the full inference succeeds.

## Pipeline B — Generate speech and render

TTS-01 adds a user-triggered `POST /projects/{project_id}/tts-jobs`. FastAPI locks the Project, re-runs EDIT-03 readiness, rejects blocking errors or another active Job, then returns a queued `tts` Job. The separate sequential worker revalidates readiness while excluding its own claimed Job, selects only missing or invalid current Segment audio for synthesis using Edge-TTS voice `vi-VN-HoaiMyNeural` by default, and stores MP3s below the Project/Job UUID path. `EDGE_TTS_VOICE` and `EDGE_TTS_CONCURRENCY` configure the Vietnamese voice and a maximum concurrency of five for the selected synthesis operations.

Adaptive pacing uses the legacy v3.4.1 whitespace-token WPS heuristic (Vietnamese syllables are counted as whitespace tokens): above 4.2 WPS use +20%, above 3.5 use +12%, above 2.8 use +6%, otherwise normal speed. Each Segment request has a 90-second timeout and at most three attempts with short bounded backoff for transient connection/service failures, including Edge-TTS `NoAudioReceived`; client/configuration errors and permanent HTTP 4xx errors are not retried. FFprobe measures every synthesized MP3 and stores positive integer `duration_ms`. Original Whisper timestamps are unchanged.

TTS-INCREMENTAL-01 uses the shared `tts_artifacts.validate_segment_tts_artifact` contract for regeneration selection, audio list/playback, and timeline planning. Reuse requires exactly one current Artifact for the Segment, matching Project/Segment/current revision, a successful producer Job with the correct operation/stage and input revision, configured voice, a permitted stored speaking rate, the exact translation/voice/rate/format fingerprint, positive duration, and a non-empty file at its canonical controlled path. A `tts_normalize` producer also requires its normalization sidecar and matching final duration, preserving existing legacy `tts`/`tts_optimize` compatibility. An invalid or ambiguous mapping is regenerated; unassignable current Artifact associations stop safely. No audio is reused across revisions. Valid optimized rates (including +35%) are reused exactly rather than recomputed from the adaptive-rate policy.

Only selected replacements are staged under the new Job directory. Before publication, one transaction locks and rechecks the Project, running Job, complete Segment and current Artifact snapshots, current voice/readiness, and the validity of reused Artifacts and their locked producer Jobs. It supersedes only old Artifacts for regenerated Segments, inserts all replacements together, validates the resulting mixed-producer set, and marks the Job `succeeded`/`tts_ready`. Reused IDs, files, metadata, rates, and producer references remain unchanged. Any synthesis, database, stale-input, or reuse-validation failure rolls back publication and removes only the new Job's unpublished TTS files. When every Artifact is reusable, the Job succeeds with zero synthesis and no output directories. The endpoint/response schema is unchanged; the service logs generated/reused counts without fake progress.

TTS-01 creates Segment-level speech audio only; it does not create a final video. The user confirmed real Project worker generation and browser playback on `demo2`, including persistence after refresh. TTS-02 adds a read-only output timeline plan and TTS-03 optimizes measured voice duration; executing video time-stretching, SRT generation, mixing, audio/video synchronization, and rendering remain future work.

TTS-02 adds read-only `GET /projects/{project_id}/tts-timeline-plan`. It verifies that the Project is translation-ready, has one current usable TTS Artifact per current Segment, and that each Artifact has a successful current-revision `tts`, `tts_optimize`, or `tts_normalize` producer Job validated by the shared TTS Artifact contract, positive measured duration, safe existing audio file, current Project/Segment/revision association, and matching translation/voice/rate fingerprint. It probes the canonical Project source MP4 with FFprobe; clients never supply storage paths. The endpoint performs no database or file writes and does not enqueue a Job. `TTSTimelinePlan` returns `project_id`, `original_video_duration_ms`, `planned_output_video_duration_ms`, `segment_count`, `stretch_segment_count`, `total_added_duration_ms`, `renderable`, `blocking_issue_count`, `issues`, `segments`, and ordered `stretch_operations`.

Original timestamps and the planned output timeline remain separate. Segment timestamps are exact integer milliseconds from the persisted decimal-second values. FFprobe video duration is rounded to nearest millisecond using half-up rounding. For each Segment, available speech time runs from its source start to the next source start, or to source video end for the last Segment; this naturally counts existing silent gaps. Audio that fits this interval causes no stretch. Otherwise, the planner inserts only the needed added time by stretching that Segment's own non-overlapping source interval `[start_ms, end_ms]`, with factor `(source_interval_ms + added_ms) / source_interval_ms`. Added milliseconds are floored at 40% of interval duration, enforcing the legacy v3.5.0 maximum 1.4× factor. The descriptive factor is rounded to six decimal places; all positions, additions, cumulative shifts, and final duration remain integer milliseconds.

Subsequent output audio positions shift by the sum of actual applied additions only; capped requested duration is never used for shifts. Original overlapping source windows are reported as warnings; when a Segment needing extra time lies in an overlapping interval, stretching is blocked and the unresolved overlap is reported. A deficit beyond the 1.4× cap is a blocking planning issue and remains in the Segment result; the plan is not described as renderable. `TTSTimelinePlan` exposes source and planned durations, per-Segment output audio positions/shifts, ordered stretch operations, issue severity, and renderability without exposing paths. The viewer shows the summary and operations and can navigate to affected transcript Segments.

This is analysis only. It does not execute FFmpeg `setpts`, original-audio `atempo`, concatenation, subtitle timing, mixing, or final synchronization. RENDER-01 must execute the returned operations and verify the resulting media against the plan.

TTS-03 adds `POST /projects/{project_id}/tts-optimization-jobs`, `GET /projects/{project_id}/tts-optimization-jobs/{job_id}`, and reuses `GET /projects/{project_id}/tts-timeline-plan`. Enqueue requires a ready current translation, valid current TTS provenance, no other active Project Job, and planner blockers that are duration/overlap conflicts the optimizer can affect. The request only creates a queued `tts_optimize` Job. The sequential worker handles it outside FastAPI/Uvicorn and only targets Segments named by blocking planner issues.

Each target starts from the stored rate generated by TTS-01's adaptive pacing. The optimizer advances through legacy-inspired rate tiers `0, 6, 14, 22, 35`, choosing only a tier above the current rate and at or below `TTS_OPTIMIZATION_MAX_RATE_PERCENT` (default 35, bounded 20–35). `TTS_OPTIMIZATION_MAX_ATTEMPTS` bounds optimization operations per Segment (default 4, bounded 1–4). Optimization operations run sequentially in stable Segment position order. The worker computes a finite Job request budget from the initially blocking Segments, their remaining allowed rate tiers, and the three-request synthesis retry cap; both operation and individual Edge-TTS request attempts are counted and enforced separately. Each attempt logs only Job/Segment/candidate Artifact IDs, rate, attempt number, exception class and numeric HTTP status when present; no text or provider payload is logged. Every generated MP3 is validated and measured by FFprobe. Rate is only a request; the planner uses the measured duration. After each bounded round the existing TTS-02 planner is rerun with candidate measured durations. Segments that already fit are never regenerated; candidates that are not shorter than their current best are discarded.

Candidates remain in a job-scoped temporary directory. Before publication, the worker verifies Project revision, Segment IDs/order/source text/timestamps/translations, and the current Artifact snapshot have not changed. Improved replacements are moved to controlled job storage and published in one database transaction; only the replaced Segment's old Artifact is made non-current, while unaffected valid Artifacts remain usable. The transaction records each replacement's job, revision, measured duration, voice, rate, and exact translation/configuration fingerprint. TTS-02 now validates a current Artifact against its own completed `tts` or `tts_optimize` Job and its stored rate fingerprint, allowing a coherent set of unchanged and optimized current Artifacts without accepting stale provenance. A provider, media, interruption, or stale-snapshot failure publishes no partial replacement set and preserves the old current audio.

An optimization Job can finish with stage `tts_optimization_complete` while the current TTS-02 plan still has blockers; this means the bounded optimization attempt completed, not that the Project is render-ready. Its result endpoint reports updated per-Segment measured durations/rates, conflicts resolved by those replacements, remaining conflict excess in milliseconds, and a recommendation to shorten the Vietnamese translation in EDIT-02 and regenerate TTS. The frontend recovers the Job and result from the backend after refresh, polls the existing Job detail endpoint while active, and automatically reloads audio and timeline analysis after success. It never changes translations or source timestamps. TTS-03 does not execute video stretch, mix audio, synchronize subtitles, or render.

TTS-04 normalizes the decoded Edge-TTS media because its MP3 output can contain substantial trailing silence that FFprobe correctly includes in the full file duration, inflating TTS-02 timing conflicts. The reusable FFmpeg service analyzes decoded samples with `silencedetect`; it only trims a confidently detected trailing silence interval reaching EOF, requires at least 500 ms, uses a conservative -60 dB threshold, and retains 120 ms of boundary padding. It does not trim leading or internal pauses. Uncertain detection preserves the original bytes with a recorded skip reason; fully silent/invalid input fails. The result is re-encoded as MP3, decoded/probed again, and the published media's measured duration is stored in the Artifact. This is media normalization, not duration-only subtraction.

Each generated Segment keeps its raw Edge-TTS MP3 alongside normalized playback media and a versioned JSON provenance sidecar containing normalization settings, original/final measured durations, removed duration, voice, rate, and translation fingerprint. Incremental TTS publishes all newly generated normalized replacements in one transaction while leaving reused Artifacts untouched. TTS-03 candidates use the same normalizer and compare measured normalized media; optimization is rejected when the current baseline has no matching normalization provenance. Existing current audio can be reprocessed without Edge-TTS through `POST /projects/{project_id}/tts-normalization-jobs`; the separate worker checks current translation/Artifact snapshots and media hashes, normalizes into job-scoped storage, then atomically replaces the full current Artifact generation while retaining voice and rate (including +35%). Artifact snapshot comparison is keyed by Artifact ID so differing database query orders cannot be misreported as stale input. `GET /projects/{project_id}/tts-normalization-jobs/{job_id}` exposes persisted Job/result details without storage paths. A failed or stale operation leaves the prior Artifact generation current. No database schema change is required because provenance is kept in controlled media sidecars and existing Artifact fields.

After normalization, playback serves the normalized file and the existing TTS-02 planner probes/uses its stored measured duration only after validating the current Artifact and normalization provenance. Successful normalization invalidates prior optimization summaries as superseded; the viewer reloads audio and retains any previous timeline plan as stale until explicit reanalysis. Remaining blockers remain visible as references while stale and blocking when a fresh plan reports them. The UI offers a separate normalization Job, reports actual processed/shortened counts and before/after measured durations, and does not claim that conflicts were resolved without planner confirmation. A failed normalization result belongs to its specific Job; timeline readiness continues to come only from the authoritative planner. Browser playback and listening acceptance on `demo2` remain pending; no real Project media was normalized during implementation verification.

TIMELINE-01 uses the existing read-only timeline plan as the sole readiness authority and guides the user from each blocking conflict to its persisted Segment translation. Saving a changed translation preserves the source transcript and timestamps; the Artifact fingerprint makes audio for the old text stale, audio serving refuses the stale Artifact, and an optimization result is marked stale when current inputs no longer match its Job. TIMELINE-UX-01 retains the last successfully fetched plan in viewer memory across translation edits and TTS Job activity. It marks that plan stale after a successful translation change or published audio change, preserves its original measurements through analysis loading/failure, and replaces it only after a successful response for the same Project passes basic response validation. The stale warning explains that blockers are references with potentially outdated measurements. Clicking a blocker uses its stable Segment ID to scroll to and select the existing transcript row, open the translation editor when requested, and seek the source video without starting playback. Missing or unavailable Segments are not silently substituted. Analysis state is not persisted: changing Projects or refreshing the browser loses the last-known plan and shows an unavailable state until a new analysis succeeds.

After edits, the user rechecks TTS readiness and enqueues the existing Project-scoped `tts` Job. The backend selects stale, missing, or invalid audio itself; no frontend Segment-selection mechanism is needed. One changed translation regenerates that Segment while valid unchanged audio (including optimized rates) is preserved. Changed text receives a newly calculated standard adaptive rate and may need the established duration optimization workflow afterward. A successful TTS, optimization, or normalization Job leaves the previous plan visible as stale until the user explicitly analyzes again; a failed analysis retains that plan and displays the error. Stale plans are never used by the viewer to enable optimization or render actions. Independently, backend enqueue/worker checks continue to require current translations, valid measured audio/provenance, valid source duration, no relevant active Job, and zero blocking conflicts; frontend stale state is not an authorization input. Timeline readiness does not indicate that a video has been rendered.

RENDER-01 adds `POST /projects/{project_id}/render-jobs`; FastAPI validates the current Project and authoritative timeline plan, then returns a queued `render` Job without invoking FFmpeg. The existing sequential worker revalidates the canonical source MP4, current translation revision, every current TTS Artifact and its measured file duration before rendering. It uses only structured planner operations and output audio timestamps; clients never submit paths, offsets, or stretch factors. A complete source interval partition is trimmed and concatenated in source order. For the legacy TTS timeline, stretch uses its planned factor through FFmpeg `setpts`; original audio, when present, is partitioned identically and slowed with matching `atempo`. Vietnamese MP3 inputs are positioned on the plan's output timeline, mixed into one AAC track, and limited against clipping. Missing source audio is supported. AV-SYNC-03 adds exact microsecond execution and stricter coverage checks for `av-sync-v1` below.

AUDIO-01 adds typed per-render `audio_settings` to the `render` Job and accepts them in the existing enqueue request. Fixed mode preserves the legacy mix with a configurable original-audio gain; Auto Ducking defaults to 0.35 background gain, 0.08 during Vietnamese speech, and 1.0 TTS gain. Gains are bounded 0–1, with ducked gain no greater than background gain. Ducking intervals come directly from the current plan's output audio starts and persisted normalized TTS durations. Overlaps and gaps up to 350 ms are merged; a 1 kHz mono PCM gain-envelope WAV applies 80 ms attack and 250 ms release without an unbounded FFmpeg expression. The envelope is a job-scoped temporary input and is removed with other render staging files. FFmpeg `amultiply` applies it after original audio has been transformed into the planned output timeline. The existing final `alimiter` (0.95 ceiling), planned-duration trim, FFprobe checks and decode verification remain in force. Ducking reduces all original audio; it does not isolate voices or Chinese speech.

To verify on an existing renderable Project, open its Project Viewer, select Fixed or Auto Ducking, review the displayed gains, and start a render. Wait for the real render Job to succeed, listen to the MP4 preview, and refresh the page to confirm the published mix and render Job settings are restored from API provenance. Change settings and verify the previous published MP4 stays available with its original settings identified until a replacement succeeds. Do not use a Project whose authoritative timeline plan has blocking issues.

The renderer uses FFmpeg `libx264` CPU encoding, `yuv420p`, AAC, VFR output, and fast-start MP4 metadata. The filter graph is written to a job-scoped file to keep Windows command lines bounded. Legacy timeline rendering retains its 100 ms stream/container duration check; that tolerance is not used as proof of joint-plan synchronization. AV-SYNC-03 joint output additionally undergoes FFprobe frame/sample coverage validation and a full FFmpeg decode before publication. A job-scoped staging directory is moved into the final UUID path; a single database transaction rechecks source/translation/timeline/TTS fingerprints, publishes one `video/mp4` Artifact, supersedes an older current rendered Artifact, and marks the Job `succeeded`/`render_complete`. Failed or stale rendering leaves the previous Artifact current and removes only the failed Job's private files. A sidecar records planned/actual duration, input fingerprint, media hashes, full audio-mixing settings and stretch/TTS provenance; joint renders use `timeline-render-v3`, while legacy sidecars remain readable. Settings remain part of render identity and are returned in current-render metadata so the Viewer distinguishes selected settings from those used for a published video. Existing `timeline-render-v1` Artifacts retain compatibility.

AV-SYNC-02 introduces a separate `av-sync-v1` typed joint timeline contract and `POST /projects/{project_id}/av-sync-optimization-jobs` / `GET /projects/{project_id}/av-sync-optimization-jobs/{job_id}`. It partitions source time at ordered Segment starts, maps every source interval once into a continuous output timeline, uses conservative integer microseconds, and reports explicit overlap/coverage blockers. The pure planner evaluates measured Artifact candidates jointly across TTS rate and video speed with a deterministic minimax distortion objective, followed by squared distortion, adjacent speed-change, and stable ID/rate tie-breaks. Slack is signed; negative slack is blocking, and zero is accepted only under verified coverage precision. AV-SYNC-02 initially persisted plans as unsupported; AV-SYNC-03 enables renderability only after source-frame coverage is measured and the renderer's strict execution checks are available.

The AV-SYNC-02 worker validates current Artifacts, probes decoded audio duration in conservatively rounded microseconds, and considers the existing Artifact plus at most two alternatives from `{0, 25, 35}` for affected Segments. It synthesizes sequentially, with no more than 3 attempts per candidate, 3 total candidates per Segment, 32 generated candidates per Job, and 96 synthesis requests as a hard upper bound. Generated files remain in Job-scoped staging; if a globally feasible plan selects replacements, the worker moves only those files and atomically supersedes/inserts Artifacts after locking and rechecking Project revision, all Segment fields, current Artifact snapshots and Artifact validity. Synthesis failure, stale input, validation failure, or DB rollback preserves the prior current generation and removes the Job's unpublished files. If no globally feasible plan exists, it persists explicit blockers and publishes no replacement audio. The source probe derives a positive frame/sample margin for the maximum supported slowdown; if frame timing cannot be measured, it returns a blocker rather than accepting zero slack. Candidate-budget exhaustion persists a blocker and cannot advertise a render-ready result. The model adds `autodub_jobs.result_json`, and PostgreSQL migration `backend/migrations/20261026_av_sync_02_joint_plan.sql` adds that column and permits rate +25% in the Artifact constraint. The migration is inspected but has not been applied; use the project's approved Supabase/PostgreSQL migration deployment process for the intended environment, then verify the column and named rate constraint without resetting or recreating tables.

AV-SYNC-03 extends the existing renderer to execute the exact current `av-sync-v1` plan. Before rendering, it verifies the successful current-revision optimizer Job, supported plan version, source video digest and decoded frame coverage duration, exact Segment IDs/order/source timestamps, selected current Artifact IDs/rates/voice/fingerprint/provenance, actual file duration and a complete source partition. Every source interval is trimmed once in source order; FFmpeg `setpts` uses `1 / selected_video_speed`, and source audio uses the reciprocal `atempo`, so background sound follows the same transformed mapping. Selected TTS Artifacts are placed at planner output timestamps after upward alignment to a 48 kHz sample; ducking envelopes use those same transformed audio intervals. Plans with blockers, negative slack, unsupported speeds/rates, stale inputs, or a source partition with no decoded frame are rejected.

For `av-sync-v1`, the optimizer's coverage margin reserves two output frames at the maximum 0.5× slowdown plus one 48 kHz sample. After encoding, FFprobe frame and audio-sample timestamps are conservatively rounded to integer microseconds. The renderer checks that every dubbed Segment interval is fully covered by contiguous decoded video frame presentation intervals, that audio sample coverage reaches the final required speech sample, that final video coverage reaches the plan duration within one observed output frame, and that decoded output frame count matches the source. It then fully decodes the candidate before atomic publication. Joint render metadata uses `timeline-render-v3` and records plan version, selected intervals/speeds, Artifact IDs, rates and microsecond speech placements. Current-render metadata/preview/download continue to require the same current Project/revision/Job/fingerprint checks. Offline synthetic FFmpeg coverage is tested; no real Project was rendered for AV-SYNC-03. No PostgreSQL migration was applied.

The API exposes `GET /projects/{project_id}/rendered-video`, `/rendered-video/preview`, and `/rendered-video/download`. All three routes share the same current-render validation: exactly one current render Artifact must belong to the requested Project and its current revision; its Job must belong to that Project, target the same revision, and be `succeeded` at `render_complete`. The service also checks the expected Project/Job UUID path, media file, sidecar metadata, file digest, and current-input fingerprint. Missing or stale results return a safe 404. Preview/download use Starlette FileResponse range handling; preview is inline and download is an attachment. The Project Viewer displays the current verified render after reload, polls the existing Job endpoint for real lifecycle stages, and enables rendering only when the current plan has zero blockers. On `demo2`, the user confirmed browser acceptance: the render Job completed at `render_complete`, preview and download were available, planned and verified duration were both 23,681 ms, and the current plan had 11 TTS Segments, 7 stretch operations, and 0 blockers. TIMELINE-01 and RENDER-01 are complete; no additional Supabase schema or dependency was needed.

## State model

Worker job states: `queued`, `running`, `succeeded`, `failed`, `interrupted`.

For JOB-01, FastAPI persists `queued` Jobs and returns their IDs immediately. The separate Python worker claims the oldest queued Job using a PostgreSQL advisory transaction lock plus `FOR UPDATE SKIP LOCKED`, and permits only one `running` Job at a time.

For JOB-02, enqueue and retry set both status and stage to `queued`. Claim sets status to `running`, stage to `claimed`, records `started_at`, and clears stale error/completion values. ASR sets `preparing_asr`, `transcribing`, and finally `transcript_ready` or `no_speech`. For a non-empty transcript, translation sets `translating`, validates complete batch responses, and transactionally writes the full translation set with stage `translation_ready`; only then does the combined `transcribe_translate` Job become `succeeded`. No-speech input skips Gemini and succeeds with stage `no_speech`. ASR or translation failures become `failed` with a bounded safe reason. The worker holds a PostgreSQL session advisory lock for its process lifetime; only after acquiring that lock does startup recovery change prior `running` Jobs to `interrupted`, set stage and `completed_at`, and store a safe reason. Interrupted work remains history and is never automatically requeued. Retry creates a new Job with the original Project, operation type, and input revision. `GET /jobs/{job_id}` returns persisted lifecycle fields; `GET /projects/{project_id}/jobs` returns that Project's persisted Jobs newest first for UI reload recovery. API `finished_at` maps to the existing timezone-aware `completed_at` column. Worker transition helpers set `succeeded`/`failed` only after real work or an explicit failure, record `completed_at`, clear success errors, and bound/redact failure summaries.

- `stage` identifies detailed processing progress.
- Persisted error information must be safe to display and useful for diagnosis.
- Project business state such as `awaiting_review` or `ready` is separate from worker state.
- A restart/interruption policy must prevent jobs from remaining silently stuck.

## Planned data entities

| Entity | Minimum responsibilities |
| --- | --- |
| `Project` | ID, name, source media reference, languages, selected voice, business state, current revision, timestamps |
| `Job` | ID, project ID, operation type, input revision, state, stage, safe error, start/end timestamps |
| `Segment` | Stable ID, project ID, order, start/end, source text, translated text, revision, warnings |
| `Artifact` | ID, project/job ID, optional Segment ID, revision, media type, controlled internal path, measured duration, translation/config fingerprint, voice and adaptive rate |

Persistent entities use UUID identifiers and timezone-aware timestamps where appropriate. The database stores metadata and controlled media references only; source, intermediate, and output file contents remain in server-managed storage. DATA-01 field definitions and constraints live in `backend/app/models/entities.py`; clients receive controlled IDs/URLs, never server absolute paths.

## Planned API groups

- Create/list/read projects.
- Upload and retrieve controlled source video.
- Read Project Segments in position order and stream the UUID-derived source video through `GET /projects/{project_id}/segments` and `GET /projects/{project_id}/video`; video responses support HTTP Range requests.
- Update only a Segment's Vietnamese translation through `PATCH /projects/{project_id}/segments/{segment_id}`. The API accepts a trimmed non-empty string up to 10,000 characters, returns the saved Segment, and allows edits only when the current revision's translation Job succeeded and no Job is queued/running. This follows the current single-user API convention; the application has no authentication layer.
- Read deterministic pre-TTS validation results through `GET /projects/{project_id}/tts-readiness`; errors block readiness while timing warnings remain informational.
- Create transcribe/translate jobs, read persisted job lifecycle state, and explicitly retry failed or interrupted Jobs as new records.
- Read/edit segments and confirm a translation revision.
- Create a readiness-gated TTS Job, list current per-Segment audio and measured durations, and stream audio through `GET /projects/{project_id}/segments/{segment_id}/audio`.
- Preview/download artifacts for the current project/revision.

Routes and payloads are finalized incrementally before frontend integration; do not prebuild every endpoint.

## Deployment and extension constraints

- Local Windows, one user, one worker, one video job at a time.
- Python 3.11 virtual environment for backend/worker.
- API keys and `DATABASE_URL` remain in backend/worker environment configuration; examples contain placeholders only and `DATABASE_URL` is never committed.
- Prefer `h264_nvenc` for rendering only when runtime checks pass; retain CPU encoding fallback.
- Server-managed storage, generated media, and sensitive logs remain outside Git; Supabase connection credentials are never committed.
- Supabase Auth, Storage, Realtime, and RLS; Redis/RQ; public deployment; accounts; and multi-user operation are excluded from the MVP unless scope is explicitly revised.
